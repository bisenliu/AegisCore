## Context

AegisCore 是包含 `common` 和 `user-services` 两个 Go module 的后端 workspace，现有能力横跨共享基础设施、HTTP runtime、响应契约、请求校验、认证、用户资料和迁移工具链。注释整改是跨模块的非功能性治理变更，目标是提升公开 API 可读性、降低维护成本，并让后续 lint 检查能够稳定发现注释缺失或不规范问题。

当前变更只补充和校正 Go 注释，不改变 controller/service/repository 分层，不修改 Ent schema 或生成代码，不影响 Redis/PostgreSQL 配置、HTTP 路由、响应信封、错误码、数据库迁移和运行时生命周期。

## Goals / Non-Goals

**Goals:**
- 为 `common/` 和 `user-services/` 中导出的 Go 标识符补充符合 godoc 规范的注释，并确保注释以标识符名称开头。
- 为复杂业务逻辑、关键分支、边界条件、魔法数字、默认值和策略参数补充简洁准确的解释性注释。
- 运行 `golangci-lint`，并修复与注释覆盖或 godoc 规范相关的问题。
- 保持注释与当前真实代码行为一致，避免把未来能力或未实现行为写入注释。

**Non-Goals:**
- 不重命名 Go 包、类型、函数、方法、常量或变量，除非 lint 明确要求且不会改变外部契约。
- 不修改 HTTP API、JSON 字段、响应码、错误消息、配置 key、环境变量、数据库 schema 或 Atlas migration。
- 不手写 `user-services/ent/` 下的生成代码；如发现生成代码注释问题，仅记录风险，不直接修改。
- 不新增业务能力、认证策略、迁移策略或运行时依赖。

## Decisions

1. 以包和能力边界分批审查 Go 源码。

   选择按 `common` 子包、`user-services/internal` 分层、`cmd`、`ent/schema`、脚本 helper 等边界逐步补充注释，而不是一次性只修复 lint 报错。这样可以覆盖 lint 当前未必启用但维护风险较高的复杂逻辑和策略参数。备选方案是只根据 `golangci-lint` 输出最小修复，但该方案容易遗漏复杂业务逻辑中的“为什么”。

2. godoc 注释优先描述公开契约，行内注释只解释不直观原因。

   导出标识符的注释必须以标识符名称开头，并说明用途、行为、重要参数、返回结果和关键错误；复杂逻辑中的行内注释只在读者无法从代码直接理解原因时添加。备选方案是为大量普通语句添加注释，但会造成过度注释和维护成本上升。

3. 注释不得替代代码或规格的事实来源。

   注释必须基于现有实现和稳定规格，不承诺尚未实现的功能。涉及外部 API、错误码、配置、数据库字段、认证和迁移策略时，以代码和 `openspec/specs/` 的当前事实为准。备选方案是借注释补充理想行为，但会造成文档与实现不一致。

4. 对魔法数字和默认值说明语义而不是强行抽常量。

   本变更只要求解释特殊阈值、超时、默认值和策略参数的来源或业务含义；是否抽取常量应遵循 `runtime-constant-governance` 的 owner 边界，不为减少字面量而新增无意义公共 API。备选方案是同步重构常量组织，但会扩大变更范围并引入行为风险。

5. lint 验证聚焦注释相关问题。

   实现完成后运行 `golangci-lint`。如果输出包含非注释类历史问题，应优先确认是否与本变更有关；本变更只修复注释缺失、godoc 风格、文档不一致和由注释导致的 lint 问题。备选方案是顺带修复所有 lint 问题，但会偏离注释治理目标。

## Risks / Trade-offs

- 注释描述与代码行为不一致 → 以当前实现、主规格和测试为事实来源，避免写入推测性行为。
- 过度注释降低可读性 → 只为导出 API、复杂逻辑、关键边界和策略参数添加注释，普通直观代码不添加行内注释。
- 触碰生成代码导致后续生成覆盖 → 不手写 `user-services/ent/` 生成文件；只处理 schema、手写运行时代码和测试代码中的注释。
- lint 暴露大量历史问题 → 将注释相关问题作为本 change 的修复边界，非注释类问题记录为后续治理事项。
- 跨模块注释风格不统一 → 使用统一规则：导出标识符 godoc 以标识符开头，复杂逻辑注释解释原因，默认值注释说明语义来源。
