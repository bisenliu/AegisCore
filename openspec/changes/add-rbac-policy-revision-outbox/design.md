## Context

当前角色状态、角色权限和用户角色在线 mutation 先由各 PostgreSQL store 提交，再由 role command service 调用 `PolicyChangeNotifier` 执行本地 reload、Redis policy version 更新和 Pub/Sub 通知。后半段拥有独立失败点：mutation 已不可回滚，但同步失败时没有数据库中的待处理事实；同时 Redis `INCR` 既承担 revision 分配又承担通知加速，无法成为可靠的业务权威。

本 change 横跨 `user-service/internal/features/role/` 写侧、`user-service/internal/features/permission/` policy sync 接口、`user-service/internal/persistence/ent/schema/` 与 `user-service/migrations/`。HTTP 契约、Casbin policy 结构和 Redis Pub/Sub 消息形状保持不变。即时 reload/Redis 通知暂时保留，但改为消费数据库已分配的 revision；即使该步骤失败，pending outbox 仍保存可恢复事实。

## Goals / Non-Goals

**Goals:**

- 为每次成功的在线 RBAC mutation 持久化全局单调 `policy_revision` 和一条唯一 pending outbox event。
- 让业务 mutation、revision 记录和 outbox event 使用同一个 Ent/PostgreSQL transaction，并统一处理 begin、业务写、revision、outbox、commit 和 rollback 错误。
- 让写后同步消费数据库 revision，禁止 Redis 分配权威版本；Redis 只缓存最新已知 revision 并传播现有通知。
- 保持 application 拥有最小写侧 port，具体 Ent transaction、predicate、表模型和错误映射留在 role PostgreSQL infrastructure。
- 以故障注入测试证明业务写、revision、outbox 或 commit 任一步失败时不存在部分提交。

**Non-Goals:**

- 不实现扫描、锁定、投递或重试 pending outbox 的 dispatcher 后台循环。
- 不让 Casbin engine、watcher 或 version tracker 按数据库 revision 实现新的 reload/ack 状态机。
- 不改变 Redis Pub/Sub 消息协议、watcher 生命周期、lag 指标、HTTP 路由、DTO 或 OpenAPI 文档。
- 不把 RBAC revision/outbox 抽象下沉到 `common/`、`internal/shared/` 或 `internal/integration/`，也不提供旧 Redis counter 权威模式的兼容分支。

## Decisions

### 1. 使用追加式 revision 记录作为 PostgreSQL 权威序列

新增 `rbac_policy_revisions` 表，每次在线 mutation 插入一行，由 PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY` 分配 `revision`，并保存 `reason`、可选 `role_id`、`user_id`、`permission_id` 和 `created_at`。成功提交的 revision 必须严格递增，但允许事务回滚造成序列空洞；消费者只能比较大小，不能假设连续。

选择追加记录而非单行 counter，是因为 revision 本身也是可审计、可关联 outbox 的提交事实，且无需在热点单行上执行显式 `SELECT FOR UPDATE`。备选的 Redis `INCR` 无法与 PostgreSQL mutation 原子提交；单行数据库 counter 虽可事务化，但会增加锁竞争且不能单独证明每次 mutation 对应的 revision 事实。

### 2. 使用一 revision 对一 outbox event 的持久模型

新增 `rbac_policy_outbox_events` 表，至少包含：内部主键、稳定 `event_id`、唯一 `revision` 外键、`kind`、`reason`、可选 `role_id`/`user_id`/`permission_id`、`status`、`attempt_count`、`next_attempt_at`、可空 `last_error`、唯一 `idempotency_key`、`created_at`、`updated_at` 和可空 `delivered_at`。初始 `status` 固定为 `pending`、`attempt_count=0`，`idempotency_key` 使用 `rbac-policy-revision:<revision>`；事件 kind 限定为当前同步语义所需的 `policy_changed` 或 `user_role_changed`，reason 沿用稳定的 mutation 原因值。

Ent 一对一关系、`revision` 唯一非空约束和同事务写入保证每个 revision 最多一条 event，且成功 mutation 必有一条 event。仓库 Atlas 流程全局禁用数据库真实外键，本 change 遵循该策略，不为单表关系引入物理 FK。对象 ID 使用 nullable UUID 列而非开放 JSON payload，便于约束、诊断和后续 dispatcher 构造现有消息，同时避免当前阶段设计未被消费的通用 eventbus/outbox 框架。event 状态和重试字段现在只建立恢复契约，不在本 change 中驱动后台执行。

### 3. 由执行 mutation 的 PostgreSQL store 拥有完整事务

role application 定义 transport-neutral 的 policy change 元数据和包含已提交 revision 的写结果；角色、角色权限、用户角色消费侧 store 方法接收对应 reason/对象 ID，并由 PostgreSQL adapter 在一个 transaction 中依次完成业务写、revision 插入、outbox 插入和 commit。完整替换继续在同一 transaction 中删除旧绑定和插入新绑定，随后才记录 revision/outbox。

采用 store 方法拥有 transaction，而不是 application 暴露 Ent transaction handle，是为了保持 application 不依赖 Ent/SQL，并确保 mutation 与 outbox 不可能被调用方拆成两个提交点。不会创建跨 feature 的通用 UnitOfWork，也不会把业务 event model 放入 permission infrastructure 或 `common`。

在线写包括角色创建、角色更新、角色启停、角色权限添加/替换/删除和用户角色添加/替换/删除。校验失败、幂等冲突和 not-found 等未产生业务 mutation 的请求不分配 revision。查询和离线 seed/bootstrap 不在本 change 的在线 outbox 范围内。

### 4. 即时同步使用已提交数据库 revision，outbox 提供恢复事实

事务提交后，command service 将 store 返回的 revision 传给 `PolicyChangeNotifier`。permission policy sync coordinator 保留当前本地 reload、用户缓存失效、Redis version 写入和 Pub/Sub 发布流程，但 Redis adapter 改为写入/传播调用方提供的 revision，MUST NOT 使用 `INCR` 或自行生成版本；写入 Redis 时不得用较小 revision 覆盖较大值。

即时同步失败仍返回现有同步错误并保持 fail-closed/可诊断语义，但不得修改或删除 pending outbox，因此 mutation 已具备后续 dispatcher 恢复所需的持久事实。该选择比本 change 直接删除 notifier 更安全，因为 dispatcher 尚未实现，完全依赖 outbox 会扩大副本授权投影的陈旧窗口；也不采用 publish 失败后回滚，因为 PostgreSQL commit 后已无法安全回滚业务 mutation。

### 5. schema 和归属边界

手写 schema 位于 `user-service/internal/persistence/ent/schema/`，生成代码只通过 `make user-service-generate` 更新；RBAC transaction/outbox helper 位于 `user-service/internal/features/role/infrastructure/postgres/`，因为它服务于 role 拥有的在线 mutation。permission feature 只拥有 policy sync 消费接口和 Redis/Casbin adapter，不直接写 outbox。

Atlas migration 创建 identity/sequence、revision 表、outbox 表、唯一约束和状态/重试扫描索引，并遵循仓库全局无数据库真实外键策略。`common/`、`internal/shared/`、`internal/integration/`、deployments、观测资产和 OpenAPI 生成物不变；`docs/openspec` 只通过本 change delta 和归档后的 `rbac-access-control` 主规格同步。

## Risks / Trade-offs

- [PostgreSQL identity 在回滚后产生 revision 空洞] → 规格只要求成功 revision 单调，不要求连续；测试不得断言相邻 revision 差值为一。
- [高并发 mutation 的 revision 分配顺序与 commit 完成顺序不同] → 权威顺序以已提交 revision 数值为准；同步端只接受更大 revision，后续 dispatcher 必须按 revision 排序并幂等投递。
- [本 change 没有 dispatcher，pending event 暂不能自动重放] → 保留现有即时同步；outbox 建立不丢失的恢复基础，dispatcher 由后续 change 实现。
- [事务范围扩大增加延迟和锁持有时间] → revision/outbox 各为单行 append，避免读取或锁定全局 counter；事务内不执行 Redis、reload、日志网络调用或其他外部 I/O。
- [即时同步失败时 API 返回错误但 mutation 已提交] → 保持当前对调用方的同步错误语义，同时通过唯一 revision/outbox 支持幂等恢复；日志必须携带低基数 reason 和 revision，不记录 SQL 或 payload。
- [迁移已应用但应用回滚] → 新表为追加式且旧应用不会访问，可保留；回滚应用不删除表。应用升级失败时先回滚二进制，后续受控 migration 再决定是否清理未使用表。
- [新应用在 migration 前启动] → 按既有发布顺序先执行并校验 migration，再滚动 user-service；缺表时写操作失败并回滚，不允许降级到 Redis 权威分支。

## Migration Plan

1. 增加 Ent schema，生成 Ent 代码，并生成、审查和校验 Atlas SQL migration；迁移只新增表、sequence、约束和索引，不回填历史 Redis version。
2. 发布前通过独立 migration Job 或受控发布平台应用 migration。
3. 部署写侧 transaction/outbox 和数据库 revision 驱动的即时同步代码；不启用兼容 feature flag，也不读取旧 Redis counter 作为权威初值。
4. 验证新 mutation 同时产生 revision/outbox，Redis 中仅出现数据库已分配 revision，并观察现有 reload/readiness 错误。
5. 如需回滚应用，恢复旧二进制并保留新增表；不得在仍有新二进制运行时删除 schema。数据库 revision 与旧 Redis counter 不做双写或对账承诺。

- 运行 schema/生成验证：`make user-service-generate`、`make user-service-migrate-diff name=add-rbac-policy-revision-outbox`、`make user-service-migrate-validate`，并检查生成物 drift。

- 运行 permission policy sync/Redis adapter 测试，证明 revision 由调用方传入、较小 revision 不覆盖较大值且不再调用 Redis `INCR`。
- 运行 `make user-service-architecture-lint`，确认 application/domain 未导入 Ent、Redis、SQL 或跨 feature infrastructure，且 outbox 未下沉到禁止边界。
- 完成本 change 后暂存预期代码、生成物、migration 和规格，再运行 `make lint` 与 `make verify`。
